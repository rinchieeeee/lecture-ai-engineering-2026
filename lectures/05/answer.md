- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  - 採用したい方式：ベクトル検索
  - 理由：
    - 今回の質問では1〜2ページ(p.51〜52)で根拠が完結しており、ベクトル検索が最も少ないトークン数(入力 3,178 tokens)・最安コスト($0.001436、全文投入の約1/25)で正確な回答と引用を出せたため。
    - Tree は埋め込みDB不要で説明可能性が高い一方、往復回数が増えて累積トークン・APIエラー遭遇リスクが上がりやすい。
    - Graph は前後ページや共通用語をたどれるため複数箇所にまたがる質問に強いが、単一ページで完結する質問では入力トークンと処理時間がやや過剰になった。
  - 比較条件の限界：
    - 全文投入は全9資料・438ページを対象としているのに対し、他3方式は第1〜3回の本講義3資料・214ページのみを対象としており、条件が完全に同一ではない。また各方式1回ずつの実行結果(単一質問)であり、APIの混雑状況や生成の揺らぎの影響を受ける。

  - 質問に「第2回の説明では」と明示されていたため Tree は迷わず p.52 にたどり着けたが、どの回・章にあるか分からない質問では Tree の探索回数が増えたり見落としたりする可能性があり、質問の性質によって有利な方式が大きく変わりそうだと感じた。

## 宿題

- 取り組んだレベル：発展
- やったこと(変更したファイル・設定・処理、または設計した取得方法)：
  - 既存の検索DB(`index.sqlite3`)と `tree.json`・`graph.json`・`glossary.json` を組み合わせてエージェント相当の構造化回答を返すパイプラインを実装([app/structured_rag.py](../../app/structured_rag.py)、比較スクリプト [scripts/compare_rag_methods.py](../../scripts/compare_rag_methods.py)、テスト [tests/test_structured_rag.py](../../tests/test_structured_rag.py)、[app/retrieval.py](../../app/retrieval.py) に事前計算済みベクトル読込ヘルパを追加)。索引の再作成はなし。
  - **設計と理由**：現行RAG単体(`python -m app.retrieval`)は複合質問を1本のベクトルで検索して生テキスト5件を返すだけのため、以下の5段構成とした。
    1. **質問分解・表記展開**：接続詞・文単位で観点(サブクエリ)に分解し、`glossary.json` の別名と表記ゆれ(例：`振る舞い`↔`ふるまい`、`事後学習`↔`ポストトレーニング`)を展開。
    2. ハイブリッドRAG：埋め込みベクトル(`gemini-embedding-001`)と軽量BM25/文字2-gramをRRF統合(API不要の `--offline` モードも併設)。
    3. **Tree検索の局所化**：`tree.json` で候補が集まる章を特定し、同章内のタイトル一致・概観・前後1ページを補完。
    4. **改良Graph展開**：現行 `search_graph` が無視していた `related_term` を含め全関係を使い、高頻度ハブ語(`LLM`, `FT`等)をIDF減衰＋クエリ誘導フィルタで枝刈りした。
    5. **棄却判定と抽出型整形**：希少語カバレッジが閾値未満なら「確認できません」を返し、根拠がある場合は著作権表記を除いて観点別の要点・対比・`第N回・PDF p.N` 引用・取得経路を整形。
